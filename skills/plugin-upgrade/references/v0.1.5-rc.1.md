### DSH-0.1.5-RC1-01 · the base bundle's default agent model id moves to `deepseek-flash`

- **Type**: behavior
- **Applies to**: every base-backed profile composition (the `dsh-base` first patch layer),
  and any deployment, preset, wrapper, snapshot, or document that names `deepseek-v4-flash`
  as the default model.
- **Touchpoints**: none (composition/config surface).
- **Action level**: required-if-hit
- **Symptoms**: the base bundle's `agent-default-model` row declares `model: deepseek-flash`
  where `dsh-v0.1.5-alpha.2` declared `deepseek-v4-flash`. New Sessions therefore start on
  DeepSeek-V41-Flash; a profile that previously inherited the default changes model
  silently, while a configuration file that names a model explicitly keeps winning.
- **Migration recipe**: grep your own profile patch, `agent.cordis.yml` presets, fixtures,
  and docs for `deepseek-v4-flash`. Accept `deepseek-flash` where the default is fine, or
  pin the previous id with your own `agent-default-model` row (`model: deepseek-v4-flash`).
  Do not assume the target gateway serves the new id yet — see DSH-0.1.5-RC1-02.
- **Verification**: `dsh --profile <name> --dump-config` shows the effective
  `agent-default-model` row; open a fresh Session and confirm the model id in its header,
  then run one real turn.
- **Source**: [rc.1 `packages/bundle/base/cordis.patch.yml`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-rc.1/packages/bundle/base/cordis.patch.yml) · [rc.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.5-rc.1)

### DSH-0.1.5-RC1-02 · `deepseek-flash` joins the adapter catalog with image input, in-history system prompts, and no gateway probe

- **Type**: capability
- **Applies to**: deployments on the `deepseek-official` provider, model-discovery consumers
  (`ctx.llm.listModels`), model pickers and settings UIs that enumerate the catalog, and
  plugins whose assumptions about the default catalog are text-only.
- **Touchpoints**: none (catalog/config surface).
- **Action level**: conditional
- **Symptoms**: the adapter's default catalog gains `deepseek-flash` (display name
  `DeepSeek-V41-Flash`, `inputModalities: ['text', 'image']`, a 1,000,000-token context
  window, and `systemPromptUpdate: 'in-history'`), while `deepseek-v4-flash`,
  `deepseek-v4-pro`, and `deepseek-v4-flash-vision-exp` stay. Two consequences matter for
  plugin and deployment authors:
  - the default entry is registered **without probing gateway availability**, so requests
    fail with `INVALID_REQUEST` on a gateway that has not enabled the id;
  - only the default `deepseek-flash` entry declares `systemPromptUpdate: 'in-history'`;
    any other model needs that declaration in an explicit `models` list, and a value other
    than `in-history` fails at load.
- **Migration recipe**: do not hardcode the previous catalog list; read it through
  `ctx.llm.listModels('deepseek-official')` where you display or select models. If your
  gateway cannot serve `deepseek-flash`, declare your own `models` list or pin the previous
  default model. If your deployment relies on dynamic system prompts without rewriting the
  leading message, declare `systemPromptUpdate: 'in-history'` on the models you route to.
- **Verification**: `ctx.llm.listModels('deepseek-official')` lists four entries; one real
  Chat Completions turn against `deepseek-flash` succeeds on a gateway that serves it; a
  turn on an `in-history` model appends a changed system prompt after the cached history
  instead of rewriting the leading system message.
- **Source**: [rc.1 `packages/llm/llm-deepseek/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-rc.1/packages/llm/llm-deepseek/src/index.ts) · [rc.1 `packages/llm/llm-deepseek/README.md`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-rc.1/packages/llm/llm-deepseek/README.md)

### DSH-0.1.5-RC1-03 · document renderers receive a required `scrollportRef` prop

- **Type**: breaking
- **Applies to**: Web Client plugins that register a `sidebar.right.tab.document` renderer.
- **Touchpoints**: #1 for source patches touching the renderer signature; none otherwise
  (client slot props).
- **Action level**: required-if-hit
- **Symptoms**: the document renderer props gain
  `scrollportRef: RefCallback<HTMLElement>`. A renderer that ignores it keeps the shared
  body as the scroll owner, and a TypeScript build fails until the new member is accepted.
- **Migration recipe**: attach the callback to the element that actually scrolls
  (`<div ref={scrollportRef}>`) and call it with `null` when your renderer stops owning the
  scrollport; pass `null` outright when the shared body should stay the owner.
- **Verification**: open a long document in the right sidebar, scroll it, switch tabs and
  return — the reading position survives; a renderer that never scrolls does not disturb
  the shared body's behavior.
- **Source**: [rc.1 `packages/client/ui-sidebar-documentpreview/src/client/document/contract.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-rc.1/packages/client/ui-sidebar-documentpreview/src/client/document/contract.ts)

### DSH-0.1.5-RC1-04 · sidebar guide entries gain an optional `description`

- **Type**: capability
- **Applies to**: plugins that register a `sidebar.right.tab.*` type or its guide entries.
- **Touchpoints**: none (client slot props).
- **Action level**: optional
- **Symptoms**: `SidebarRightGuideEntry` gains optional `description?: () => string`, read
  fresh on every use like `title`, so switching the interface language needs no
  re-registration. The guide renders it only while its entry list stays light and falls
  back to titles alone when crowded, so a type must still stand on its title. `icon` now
  falls back to the guide's cube placeholder when omitted. The builtin `files` tab adopts
  both (its definition moved from `definition.ts` to `definition.tsx` and added two locale
  keys).
- **Migration recipe**: add `description: () => t('guide.description')` (with the matching
  locale key pair) where one line explaining what opens helps the user; keep the title
  self-sufficient and keep thunked copy so language changes need no re-registration.
- **Verification**: open the right sidebar guide in a Session with several tab types and
  switch the UI language — title and description update without a reload; a crowded guide
  degrades to titles only.
- **Source**: [rc.1 `packages/client/ui-sidebar-right/src/client/tab-registry.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-rc.1/packages/client/ui-sidebar-right/src/client/tab-registry.ts) · [rc.1 `packages/client/ui-sidebar-files/src/client/definition.tsx`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-rc.1/packages/client/ui-sidebar-files/src/client/definition.tsx)

### DSH-0.1.5-RC1-05 · no other plugin-facing surface moved (negative evidence plus a fleet verification record)

- **Type**: behavior
- **Applies to**: every plugin and profile wrapper upgrading from `dsh-v0.1.5-alpha.2`.
- **Touchpoints**: none.
- **Action level**: informational
- **Symptoms**: `packages/core/tools`, `packages/core/agent`, `packages/client/connection`,
  `packages/skill/*`, and `packages/session/session-persistence` differ from
  `dsh-v0.1.5-alpha.2` only in `package.json` version strings. `engines`
  (`^22.19.0 || >=24.0.0`), vendored `@deepseek-ai/cordis` (`4.0.0-rc.7`, upstream
  `56b3d4f7…`), and `SESSION_FORMAT_VERSION` (`3`) are unchanged, and the tool, agent, and
  skill APIs are untouched — the release-notes "chores" list summarizes the whole 0.1.5
  line, not this edge.
- **Migration recipe**: no source action for a plugin that already runs on
  `0.1.5-alpha.1`/`alpha.2`. Re-run your own project checks after the version bump, and put
  the risk budget on the earlier edges of the corridor.
- **Verification**: this card set's authoring pass ran a 17-repository plugin fleet against
  `dsh-v0.1.5-rc.1` on a source checkout (Windows 11, Node 22.19.0): 15 repositories pass
  `npm run check`, `dsh-toolkit` passes its four suites (723 vitest cases for `test:all`),
  `dsh-plugin-dev` passes its skill-form check, every plugin needed zero source changes, and
  14 mounted plugins answered through the live Web host.
- **Field note** (2026-09-10, omdsh-dev fleet, Windows 11 + Node 22.19.0): two harness
  regressions introduced at `0.1.5-alpha.1` are still present in `rc.1` and are **not** part
  of this edge — the V2→V3 payload validator still refuses plugin-declared
  `MessageSourceMap` kinds (every Session containing one fails to load), and
  `connection.rpc.handle()` still cannot resolve `webServer` for a third-party channel
  (the channel registers but gets no HTTP route). Both were reproduced on the rc.1 tag with
  local patches and are reported against the `0.1.5-alpha.1` edge cards; a deployment at or
  above `0.1.5-alpha.1` must account for them until upstream fixes them.
