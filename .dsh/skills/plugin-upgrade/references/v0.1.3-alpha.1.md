### DSH-0.1.3-A1-01 · v0→v1 migrator refuses 0.1.2-alpha.x session logs (`replayState` `kind`)

- **Type**: breaking
- **Applies to**: Host plane. Any deployment upgrading from 0.1.2-alpha.x with real session history to 0.1.3-alpha.1; any plugin/integration that reads session logs across this boundary inherits the same refusal through the persistence layer.
- **Touchpoints**: #2, #4
- **Action level**: required-if-hit
- **Symptoms**: the 0.1.3 Web UI shows
  `Failed to load history: failed to observe session "session-<id>": @deepseek-ai/dsh-session-format-v0-to-v1 refuses this format v0 Session: assistant/chunk 95 chunk replayState has unexpected member "kind"; source v0 artifact remains unchanged (raw log: …)`.
  What looks like "slow loading" before the failure is the migration scan itself (40 s+ for
  a ~16 MB log, no progress or error surfaced while it runs).
- **Migration recipe**: none available yet. Do not hand-edit v0 logs — the migrator is
  fail-closed and leaves the source artifact unchanged, so nothing is corrupted, but the
  session stays blocked. Until an upstream fix or an official rewrite path exists, keep a
  0.1.2-rc.1 installation available for reading old logs (rc.1 loads them natively — it has
  no v0→v1 migrator on this path).
- **Verification**: after an upstream fix lands, open a previously refusing session on
  0.1.3; message and tool-card counts must match the 0.1.2-rc.1 rendering of the same log.
- **Source**: measured 2026-09-05 on the release-tarball build `0.1.3-alpha.1-9523542`; the
  refusal string reproduced on two sessions (15.7 MB / 19 MB logs, refusing at chunks
  ~95/~94) out of a 6-session real-history batch (same writer family, all refused). Full
  evidence chain (build identity, CDP timing, raw refusal strings, three-leg attribution):
  [upstream-0.1.3 adaptation audit, pinned](https://raw.githubusercontent.com/alex04130/dsh-forge/8ab0b148b2382b2a33158039fd10d7625b4e145a/docs/audits/upstream-0.1.3-adaptation-audit.md)
  (§0/§7/§7.5). Official writer coordinates: `@deepseek-ai/dsh-llm-pi-ai` `toPiReplayState()`
  in the installed 0.1.3-alpha.1 tree (`response.kind: "pi-ai"`, `version: 2`) — this
  version is distributed via the release-tarball channel and is not on npm
  (`latest`/`alpha`/`next` = 0.1.2-rc.1/alpha.5/0.1.2-rc.1, registry checked 2026-09-06);
  re-verify against the official tag once it is published.
  Comparison control: the same batch loads natively on 0.1.2-rc.1 (no migration face) and
  in the 0.1.2-alpha.3 writer home.

Root cause (observed shape) — the refused member is written by official core, not plugins.
Three-leg proof, measured 2026-09-05:

1. **Plugin negative scan**: zero hits for `replayState` / `assistant/chunk` writes across
   all local plugin sources (dynamic plugins, profile plugins, community plugins).
2. **Official writer**: the pi-ai adapter `@deepseek-ai/dsh-llm-pi-ai` constructs the
   replay envelope itself in `toPiReplayState()` — `response.kind: "pi-ai"`, `version: 2`
   (installed tree, official package).
3. **Older writer generation layered in the append-only log**: the refused
   `assistant/chunk` events carry
   `replayState: {kind: "pi-ai", version: 1, api: "openai-completions", …}` — `kind` at the
   top level with `version: 1`, emitted by the pre-alpha.4 writer generation and preserved
   verbatim in the append-only log. The 0.1.3 `dsh-session-format-v0-to-v1` migrator
   validates `replayState` against a single-generation schema, so it rejects the layered
   older-generation member and refuses the whole session (fail-closed; the source v0
   artifact stays unchanged — good safety behavior, but the net result is a hard block on
   history).

```json
{"type":"assistant/chunk","seq":95,"data":{"turn":1,"step":1,"chunk":{"type":"finish","reason":{"kind":"tool-calls"},"replayState":{"kind":"pi-ai","version":1,"api":"openai-completions","provider":"…","model":"…","responseModel":"…","responseId":"…","stopReason":"toolUse","blocks":[…]}}}}
```

`replayState.kind` at the top level with `version: 1` marks the older writer generation; the
current official writer nests `kind` inside `response` with `version: 2`.

- **Field note** (2026-09-05, reporting deployment): performance contrast on the same
  15.7 MB session — 0.1.2-alpha.3 opens it in ≈3.0 s (headless CDP measurement); 0.1.3
  spends 40–200 s scanning before refusing, with an undifferentiated "Loading history…"
  state. Expected behavior: accept the writer-family discriminator (or provide a documented
  0.1.2→0.1.3 log rewrite path), and surface per-session migration progress/failure
  promptly instead of an indefinite loading state.

### DSH-0.1.3-A1-02 · cross-version `resume` on 0.1.2-alpha.3 logs reports `cursor behind the last applied entry`

- **Type**: behavior
- **Applies to**: Host plane. Deployments on 0.1.3-alpha.1 resuming a session whose log was
  written by 0.1.2-alpha.3 (fresh log — distinct from the refused-history case in
  DSH-0.1.3-A1-01).
- **Touchpoints**: #2
- **Action level**: required-if-hit
- **Symptoms**: resuming such a session on 0.1.3 reports
  `cursor behind the last applied entry (gateway/internal)`; the resumed turn does not
  start.
- **Migration recipe**: none yet. Do not retry blindly — the error surfaces as a
  `gateway/internal` failure; only retry when the operation is confirmed idempotent. Keep
  the 0.1.2 line available for resuming these sessions until an upstream fix or a
  documented resume-migration path exists.
- **Verification**: after an upstream fix, resume the same session on 0.1.3; the resumed
  turn must append to the log and stream a reply without the cursor error.
- **Source**: measured 2026-09-05 on the same release-tarball build
  `0.1.3-alpha.1-9523542`; single observed case (fresh 0.1.2-alpha.3-written log) — scope
  intentionally narrow, treat as a reproduction record pending wider confirmation.
  Evidence context:
  [upstream-0.1.3 adaptation audit, pinned](https://raw.githubusercontent.com/alex04130/dsh-forge/8ab0b148b2382b2a33158039fd10d7625b4e145a/docs/audits/upstream-0.1.3-adaptation-audit.md).

### DSH-0.1.3-A1-04 · profile boot installs the outbound HTTP(S)/ALL_PROXY policy before the first plugin mounts (`dsh-http-proxy`; `$DSH_HOME/.env` may declare proxy names)

- **Type**: behavior
- **Applies to**: host deployments and profile wrappers behind corporate proxies (or that
  set `http_proxy`/`https_proxy`/`all_proxy`/`no_proxy`); plugins issuing outbound
  `fetch()`/`globalThis.fetch` requests inside the host tree; launcher scripts and CI that
  previously set `NODE_USE_ENV_PROXY=1`.
- **Touchpoints**: none (host network/environment surface; #7 only when a spawned
  subprocess must inherit the policy).
- **Action level**: required-if-hit
- **Symptoms**: `runProfile` now calls `installProxyFromEnvironment(...)` on the launcher's
  environment snapshot **before any entry mounts** and disposes the policy at shutdown
  (`apps/cli/src/profile-boot.ts` at `dsh-v0.1.3-alpha.1`); the launcher gains the new
  runtime dependency `@deepseek-ai/dsh-http-proxy`. Effect: outbound traffic on
  `fetch()`/`globalThis.fetch` (LLM requests, web_search, MCP over HTTP, sandbox SDK
  lanes) honors the proxy environment — lowercase variable names win, `ALL_PROXY` covers
  both schemes, HTTPS falls back to the HTTP proxy; loopback destinations (`localhost`,
  `127.0.0.0/8`, `::1`, `0.0.0.0`, v4-mapped) always connect direct; invalid values
  (SOCKS/PAC/unresolvable/unsupported scheme) print a per-variable warning to stderr and
  that scheme falls back to direct — startup is never blocked. Values are resolved from
  the exported environment and then from `$DSH_HOME/.env`; `dsh-app-boot` now lets the
  **home-layer** `.env` declare proxy names (`HOME_LAYER_PROXY_NAMES`), while a
  project/invoking-directory `.env` still refuses them (bootstrap-only rule, pre-existing
  at rc.1). Child processes inherit the policy through `NODE_USE_ENV_PROXY` on Node
  ≥22.21/24+; code-runtime/workflow workers and OTLP telemetry intentionally stay direct.
  Previously Node's `fetch` ignored the proxy environment, so proxy users saw direct
  connections.
- **Migration recipe**: proxy users export the variables or declare them in
  `$DSH_HOME/.env`, restart the profile, and verify egress (LLM call + web_search) now
  crosses the proxy; drop now-unneeded workarounds that injected custom dispatchers or set
  `NODE_USE_ENV_PROXY=1` for profile boots. Plugin authors: do not construct bare undici
  `Agent`/dispatchers for host-tree requests — they bypass the policy; where a custom
  transport is unavoidable, consult the `dsh-http-proxy` README at the target tag (E2B SDK
  integrations use its `proxyRouteFor`). When no proxy should apply, leave the variables
  unset or set `no_proxy` explicitly.
- **Verification**: with a recording local proxy configured, a headless/session request
  appears in the proxy log and a loopback target does not; a bogus proxy value prints the
  `dsh: ...` stderr warning and still connects direct; a proxy declared in `$DSH_HOME/.env`
  is honored, while the same name in the invoking directory's `.env` makes the launch
  refuse with the bootstrap-only message.
- **Source**: [alpha.1 `dsh-http-proxy` README (resolution order, loopback, invalid-value behavior, child-env notes)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/util/http-proxy/README.md) · [alpha.1 `profile-boot.ts` (`installProxyFromEnvironment` before first mount)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/apps/cli/src/profile-boot.ts) · [alpha.1 `dsh-app-boot` `HOME_LAYER_PROXY_NAMES`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/boot/app-boot/src/index.ts) · [alpha.1 release notes (HTTP(S)_PROXY support)](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1) · [dsh-v0.1.2-rc.1...dsh-v0.1.3-alpha.1](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.1.2-rc.1...dsh-v0.1.3-alpha.1)

### DSH-0.1.3-A1-05 · session persistence moves to a lifecycle-held `SessionHandle`; `agentLoop.create()` is async with a per-session lock

- **Type**: breaking
- **Applies to**: host/session-plane integrations that call or implement
  `ctx.sessionPersistence` (`create`/`open`/`stat`/`list`) outside the official bundles,
  out-of-tree persistence providers, code that creates agents through
  `agentLoop.create(...)` (or factories wrapping it) synchronously, and multi-process
  deployments sharing one session store.
- **Touchpoints**: #2
- **Action level**: required-if-hit
- **Symptoms**: `@deepseek-ai/dsh-session-persistence` at `dsh-v0.1.3-alpha.1` adds a
  handle layer (`packages/session/session-persistence/src/handle.ts`):
  `SessionPersistence.create`/`open` return a `SessionHandle` — an `AsyncDisposable`
  per-session channel with `SessionAccess` `read` or `write`. A `write` handle is the
  session's single mutator (it also reads its own log); a `read` handle never takes
  ownership and works while another handle or process holds `write`. `close()` is the one
  teardown (idempotent; `Symbol.asyncDispose` delegates to it), and every operation on a
  closed handle rejects with `SessionHandleClosedError`. The error surface gains
  ownership errors (`SessionAlreadyOwnedError`, `SessionOwnershipLostError`,
  `SessionReadOnlyError`, `SessionAlreadyExistsError`). `AgentLoop.create(...)` becomes
  `async` (`Promise<Agent>`): creation awaits the stored-session backend
  (`createStoredSession`), appends any unstored suffix, and configured/restore startup
  paths await creation and report configured-startup failures instead of firing and
  forgetting. Release notes state the new session lock: the same session is held by at
  most one process.
- **Migration recipe**: `await` every `agentLoop.create(...)` call site (startup/restore
  paths and tests included); treat the handle as single-owner lifecycle state — acquire it
  through `create`/`open` with the access you need and release it with `close()` /
  `Symbol.asyncDispose`; never cache a `write` handle as a shared service; where another
  process may own the session, handle `SessionAlreadyOwnedError` /
  `SessionOwnershipLostError` explicitly (re-acquire `read` access or coordinate the
  owner — do not blind-retry writes); update fakes/test doubles to the handle shape and
  keep `read` handles working while a writer is active.
- **Verification**: typecheck passes after awaiting `create`; a second `write` open of an
  owned session rejects while a `read` open succeeds; an agent created with `await
  agentLoop.create(...)` runs a full turn and its log appends persist; using a closed
  handle rejects with `SessionHandleClosedError`.
- **Source**: [alpha.1 `session-persistence/src/handle.ts` (new)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/session/session-persistence/src/handle.ts) · [alpha.1 `session-persistence/src/errors.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/session/session-persistence/src/errors.ts) · [alpha.1 `agent-loop` (async `create`)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/core/agent-loop/src/index.ts) · [rc.1 `agent-loop` (sync `create`)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-rc.1/packages/core/agent-loop/src/index.ts) · [alpha.1 release notes (SessionHandle; async `agentLoop.create()`; session lock)](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1)

### DSH-0.1.3-A1-06 · Session log format moves to v2 with a released adjacent-generation migration stack (`session-format-catalog`)

- **Type**: behavior
- **Applies to**: integrations that read stored Session logs (raw JSONL archives,
  analysis tooling) or persist session events outside the official read APIs; out-of-tree
  `ctx.sessionPersistence` providers that must store/emit the current format.
- **Touchpoints**: #2
- **Action level**: conditional
- **Symptoms**: at `dsh-v0.1.3-alpha.1` the session tree gains
  `@deepseek-ai/dsh-session-format-catalog` (new package; `src/current.ts` + generated
  tables) as the single source for the currently installed Session format, together with
  a released adjacent-generation migration stack (architecture note
  `2026-08-31-released-session-format-migrations`, present at alpha.1, absent at rc.1).
  Writer-generation semantics matter to readers: the current official writer nests
  `replayState` inside `response` (`version: 2`), while older writer generations layered
  top-level members (`kind`, `version: 1`) into append-only logs; the migrator refuses
  unknown mixed generations fail-closed — measured refusal and resume-cursor cases are
  carded separately in [DSH-0.1.3-A1-01](v0.1.3-alpha.1.md) and [DSH-0.1.3-A1-02](v0.1.3-alpha.1.md).
- **Migration recipe**: prefer the official read surface (a `SessionHandle` `read`, or the
  0.1.2 read API `seq`/`eventAt()`/`snapshotEvents()`) over hand-parsing stored
  artifacts. Tooling that must read raw artifacts should validate against the catalog's
  current/generated shapes and treat unknown or mixed writer generations as migration
  cases rather than parse errors; never hand-write session logs. Providers implementing
  persistence must store the catalog's current format.
- **Verification**: a v2-written session and an older-writer session both read correctly
  through the official APIs; a raw-artifact reader using the catalog accepts current
  artifacts and deterministically reports the refusal cases in DSH-0.1.3-A1-01/A1-02.
- **Source**: [alpha.1 `session-format-catalog/src/current.ts` (new)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/session/session-format-catalog/src/current.ts) · [released session-format migrations note (alpha.1)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/.agents/notes/implemented/architecture/2026-08-31-released-session-format-migrations.md) · [alpha.1 release notes (Session format v2; adjacent-generation migration)](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1) · measured refusal/resume cases: DSH-0.1.3-A1-01 / DSH-0.1.3-A1-02 (this file)

## Corridor status

- First five cards for the 0.1.2 → 0.1.3 boundary. DSH-0.1.3-A1-01/A1-02 are session-log
  plane findings from one deployment's real-history upgrade trial, measured on the
  release-tarball build `0.1.3-alpha.1-9523542`; DSH-0.1.3-A1-04…A1-06 are anchored to the
  official git tags (`dsh-v0.1.2-rc.1` → `dsh-v0.1.3-alpha.1`, source-tag diff). This is
  still not a complete 0.1.3 API sweep.
- A1-01/A1-02 are fail-closed reader behaviors acting on official writer output. Plugin
  sources were negatively scanned (zero `replayState` / `assistant/chunk` writes) as part of
  the attribution, so the corridor edge is between official writer generations, not caused
  by third-party plugins.
- A1-04…A1-06 were curated from the tag diff without a real-host cold start (Windows-only
  analysis environment); verify on a real host before treating them as `reviewed`.
- Remaining alpha.1-edge surfaces in the release notes (generic file upload, `read_image`
  inline rendering, Python SDK macOS x64 wheel) carry no plugin-facing API coordinates in
  this analysis — treat them as uncarded rather than proven-unchanged.
- npm note: 0.1.3-alpha.1 was never published to npm; npm upgrades first meet A1-04…A1-06
  at 0.1.3-alpha.2 (see the 0.1.3-alpha.2 corridor card set for that edge's own cards).
