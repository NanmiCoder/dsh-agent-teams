# AgentTeams 固定核心协议与可选查询

队长从首次模型请求起保留精简后的核心协作规则、原有 13 个业务工具和 `agent_teams_open`。普通问答、打开入口、创建/批准团队、归档团队和再次打开，都不改变插件提供的系统提示词与工具定义。成员的四个团队工具和简短说明在首次模型请求前确定，并保留原有 persona 与普通编程/研究工具。

`agent_teams_open` 是可选的只读查询工具，返回当前团队摘要、模板名称、用途/协议摘要、规划模式及成员/任务数量。描述和协议各折叠空白并截到 240 字符；这些是帮助选择的摘要，不替代创建时的完整配置和冻结快照。传入 `profile` 可只查询一个模板。与当前团队模板冲突时返回 `requested_profile` 和 `profile_conflict`，不会切换模板。它不创建团队、批准计划、恢复暂停、确认邮箱消息或触发调度。配置了模板时，原有的精简模板目录仍在安装时固定进入队长 system，保证旧 13 工具白名单也能发现模板；未配置模板时不增加目录内容。

核心规则不依赖工具结果。旧白名单只放行 13 个业务工具时可直接规划；代码模式没有打印 `open` 结果、工具结果被裁剪、历史被摘要替换后，核心规则仍然存在于后续请求的 system 中。需要读取可选查询数据时，代码模式应显式打印或返回数据。

| 会话身份 | 固定团队工具 | 固定 system 内容 | 可选查询 |
|---|---|---|---|
| 普通会话、队长、冷恢复的队长 | 原有 13 个业务工具 + open | 触发边界、审批、协作、attempt、质量门禁、暂停/恢复、收尾规则 | 当前团队摘要、模板用途及规划模式 |
| 成员 | claim、update、send_message、status | 成员规则和原有 persona | 原有任务分派与消息 |

Slash command、明确的自然语言请求和已有团队续聊均直接适用核心协议，不再要求先调用入口。解释、否定或引用 AgentTeams 本身不构成开工请求。无团队时先完成 staged 规划并等待审批；已有团队继续当前工作。

业务工具只注册一次。成员范围同时适用于原生 schema 和 PTC SDK，不能解除用户或 preset 的限制。成员身份来自持久化成员 ID、退休成员索引或插件正在执行的可信成员创建登记，不凭可自由填写的 label 判断。HMR 清理旧插件资源并恢复身份；部署新版本本身可能改变前缀，稳定性约束针对同一版本、配置下的业务生命周期。

## 方案取舍

第一版在 open 后把 1 个工具变为 14 个，并替换系统提示词。用户提供的 DeepSeek 实测中，open 前缓存读占输入比例约 97.54%，下一步约 0.64%，再下一步恢复约 94.97%。这说明一次切换也可能损失已有长历史的缓存，不能仅按工具字节数判定省钱。因此已撤回动态切换。

第二版保留固定工具和短系统说明，把核心协议移到 open 返回。独立审查发现这会让原有工具白名单、丢弃返回值的代码模式、压缩历史和没有 open 记录的旧会话依赖额外的信息获取步骤。本版将精简的核心规则固定在 system 中，保留已有精简模板目录，仅把补充元数据与状态作为可选查询结果。

这里保证本插件的业务状态不会主动改写 system/tools；供应商缓存仍受其他宿主内容、过期策略等影响。固定字节数不等于 token、缓存命中率或费用。调用 open 会增加一次模型往返和相应历史，它没有强制前置要求。

## Web 批准通知

Web 的 Approve & Run 在批准提交并启动调度后，通过 `captain.steer` 追加插件来源的控制消息。队长空闲时开始一轮，运行时在后续步骤收到消息。消息说明已经批准，不要再次批准或重复派工；处理报告/用户工作后，在只剩等待时结束轮次，成员报告自动唤醒队长。模型自己调用 approve 的路径已有工具返回，不额外发第二份通知。

用户提供的案例中，三个成员已启动，但导出时尚未发送团队报告，不能据此推断报告投递损坏。批准通知失败会记录日志，已经提交的批准不会被误报成失败；当前没有跨进程持久化重试保证。

## 验证标准

`pnpm verify:capabilities` 使用真实 scoped registry、prompt assembly 和 WorkerThreadCodeRuntime，覆盖固定核心规则、旧工具白名单直接业务调用、用户 restriction、取消/失败、可信成员身份、暂停与模板冲突、冷恢复、HMR、PTC/both SDK 及真实结果裁剪。

`scripts/harness-runtime-verify.mjs` 将打包产物安装到隔离 profile，通过发布版 CLI 和真实 Loader 启动。仅外部 LLM 是确定性 fixture；工具、会话、持久化、调度和成员创建均走生产实现。

- `progressive-entry` 保留中文/英文自然语言、原始 slash、宿主 command registry、profile alias、`--profile` 六条路径。检查 staged 无子会话、只读重新打开、显式批准、成员执行和回报；再归档、普通续聊和重新打开。自然语言路径先进行 30 轮普通对话，对所有请求的 system 与 tools 哈希分别检查不变。
- `protocol-compatibility` 用原有 13 工具白名单直接创建计划、恢复同一会话，并真实调用宿主 `compactNow` 后直接修改原计划；另一条路径用真实代码运行时丢弃 open 返回、触发裁剪及压缩，再修改原计划。逐次检查核心规则仍在模型请求中。
- `web-approval` 通过真实 HTTP 路由和宿主鉴权批准，检查队长收到批准消息、结束等待轮次、成员报告再次唤醒，以及重复/失败批准不产生成功通知。
- 保留 lifecycle、fallback、failure、captain-idle-wakeup 和两组冷恢复场景。

```sh
pnpm build
pnpm verify
pnpm pack --pack-destination /tmp/agentteams-artifacts
node scripts/harness-runtime-verify.mjs \
  --host-version 0.1.2-rc.1 \
  --artifact /tmp/agentteams-artifacts/nanmicoder-dsh-agent-teams-0.1.16-rc.1.tgz \
  --report-dir /tmp/agentteams-runtime-rc1
```

对 `compatibility.json` 每个支持版本使用独立 runtime/report 目录验证同一产物。报告保留实际请求快照、请求哈希、产物/fixture 哈希和业务断言；结果见 [verification JSON](./progressive-loading-verification.json)。确定性 fixture 证明链路和实际请求内容，不证明真实模型理解或业务质量。

真实模型对照必须使用同一供应商、模型、输入和隔离任务，比对旧版与新产物。验收以外部可核对的任务状态、各成员报告、工作区约束和实际 usage 为准，不以模型自述完成为准；旧团队冷恢复还需确认团队/成员身份不变。少量案例只能证明所测范围，不代表任意业务或长期费用。
