### DSH-0.1.6-A1-01 · `agent/session-start` is deleted and `agent/created` becomes a serial, awaited initialization event carrying `source` and `signal`



- **Type**: breaking
- **Applies to**: Host plugins that listen for agent/session lifecycle — hook bridges, session-start context injectors, goal drivers, agent-team recovery, custom agent registries — and any plugin that calls `ctx.agents.register()` / `ctx.agents.announce()` or implements an agent factory with `publish()`.
- **Touchpoints**: #2 for the internal event name that disappeared and the lifecycle event whose payload changed; #3 for the `agents` service methods whose signatures and return types changed.
- **Action level**: required-if-hit
- **Symptoms**: on rc.2 a plugin could subscribe to the session lifecycle with `ctx.on('agent/session-start', ({ agent, source }) => …)`, declared as `'agent/session-start'(this: Scoped<Agent>, payload: { agent: Agent; source: SessionStartSource }): void` at `packages/core/agent/src/runtime-types.ts:316` (`@mode emit` at `:314`). On 0.1.6-alpha.1 that event **does not exist**: a whole-snapshot text search finds 90 `agent/session-start` occurrences in rc.2 and only 6 in 0.1.6-alpha.1, all of them prose inside `.agents/notes/archived/…`. A listener left on the old name therefore never runs and produces no error and no warning, so a hook that injected context at session start silently stops injecting. The replacement is the same event, widened: `'agent/created'(this: Scoped<Agent>, payload: { agent: Agent })` with `@mode emit` at `packages/core/agent/src/runtime-types.ts:258` becomes `'agent/created'(this: Scoped<Agent>, payload: { agent: Agent; source: SessionStartSource; signal?: AbortSignal }): undefined | Promise<undefined>` at `:261` with `@mode serial` at `:259`, documented as "Listeners run in order and are awaited before creation resolves. AgentLoop holds queued input until all listeners finish. A throw or rejection fails creation and skips later listeners." The service side moved in step: `register(agent: Agent): () => void` at `packages/core/agent/src/index.ts:434` (which fired and forgot, only warning on a returned rejection at `:553`) becomes `register(agent: Agent): ReturnType<Context['effect']>` at `:434` with `await this.announce(agent, 'startup')` at `:437`; `announce(agent: Agent): void` at `:533` becomes `async announce(agent: Agent, source: SessionStartSource, signal?: AbortSignal): Promise<void>` at `:534`, dispatching `await this.ctx.serial(entry.carrier, 'agent/created', { agent, source, …signal })` at `:547`. In the loop, `publish(source: SessionStartSource): AgentHandle` at `packages/core/agent-loop/src/index.ts:218` is now `publish(source: SessionStartSource): Promise<AgentHandle>` at `:217`, and the pair `loopCtx.agents.announce(agent)` at `:670` plus `emitAgentEvent(loopCtx, agent, 'agent/session-start', { source })` at `:675` collapses to `await loopCtx.agents.announce(agent, source, abort.signal)` at `:674`. The generated routing table lost its entry too: `'agent/session-start': args => (args[0] as Record<string, unknown>)['agent'],` at `packages/core/scope/src/scoped-events.generated.ts:21` has no counterpart in the new `:11-:37` block.
- **Migration recipe**: replace every `ctx.on('agent/session-start', ({ agent, source }) => …)` with `ctx.on('agent/created', ({ agent, source, signal }) => …)`; the in-repo reference migration is `packages/hooks/hooks-claude-code/src/index.ts:205` → `:202`, which now reads `ctx.on('agent/created', async ({ agent, source, signal }) => {`, with the same change in `packages/hooks/hooks-codex/src/index.ts:187` and `packages/goal/goal/src/index.ts:255`. If the handler did asynchronous work (reading hook config, running a hook subprocess, injecting context), make it `async` and `await` that work: the dispatch is serial and awaited now, and a rejection fails agent creation instead of being logged and dropped, so a handler that must not break creation has to catch its own errors. Do not `await agent.whenIdle()` or the owner's disposal inside the listener — that is the documented deadlock. If the plugin registers agents by hand, `await` the value `ctx.agents.register(agent)` returns before using the agent. If the plugin implements its own agent factory, `publish()` must now return a promise the caller awaits.
- **Verification**: register one `agent/created` listener that records `payload.source` and confirm it observes `'startup'` for `ctx.agentLoop.create(...)` and `'resume'` for `resume(...)`, while a control listener still registered on `agent/session-start` observes nothing. Then make the `agent/created` listener throw and confirm agent creation *rejects*; on rc.2 creation succeeded and the failure was only logged.

### DSH-0.1.6-A1-02 · startup strictness moves to `auditStartupEntries`, the two `assertEntries*` helpers are gone, and a resolved `Loader.create()` no longer proves activation



- **Type**: breaking
- **Applies to**: Host plugins, launchers and profile wrappers that boot or audit a config tree through `@deepseek-ai/dsh-app-boot`, and any plugin or preset code that assumed a failed sibling row would roll the tree back.
- **Touchpoints**: #3 for the app-boot exports a launcher calls and the new `pluginPackages` service; #5 for the plugin-registration contract that a partially applied tree now leaves in place.
- **Action level**: required-if-hit
- **Symptoms**: on rc.2 `@deepseek-ai/dsh-app-boot` exported two audit helpers — `export function assertEntriesLoaded(ctx: Context, binName: string): void` at `packages/boot/app-boot/src/index.ts:685` and `export async function assertEntriesActivated(ctx: Context, binName: string): Promise<void>` at `:722`, the latter documented as "Reject a settled Loader tree when an enabled entry failed or remains inactive". On 0.1.6-alpha.1 both symbols are deleted and the only audit is `export async function auditStartupEntries(ctx: Context, binName: string, warn: (line: string) => void = line => void process.stderr.write(line)): Promise<void>` at `:818`, whose policy is much narrower: `const requiredStartupEntryIds = new Set<string>(['agent-loop', 'webserver', 'modules', 'connection', 'headless-runner', 'acp', 'sdk-jsonrpc-server'])` at `:711`; a listed id that is absent or `disabled` is ignored, a listed id that is present, enabled and inactive rejects startup (`:832-:834`), every other inactive entry produces one `warning` line and leaves successful siblings running (`:831`), and a throwing `disabled` expression counts as an entry failure rather than as disabled (`:758-:761`). The Loader itself is non-transactional again, so an activation failure leaves the new options and a failed fiber in place — the decision note says plainly that "awaiting `Loader.create()` alone does not establish activation". The preset mount path changed shape for the same reason: `export function inactiveRows(tree: EntryTree): string[]` at `packages/preset/agent-presets/src/mount.ts:302` is now `export async function inactiveRows(tree: EntryTree): Promise<string[]>` at `:301`. The same module also gained a new public service: `packages/boot/app-boot/src/index.ts:56-:60` now exports `PluginPackages`, `type PluginPackage`, `type PluginPackagesConfig`, declared on the context as `pluginPackages: PluginPackages` (`packages/boot/app-boot/src/profile-resolution/service.ts:16-:21`, `super(ctx, 'pluginPackages')` at `:68`) with `packageOf(specifier, parentURL)` at `:98`.
- **Migration recipe**: replace `assertEntriesLoaded(ctx, bin)` + `assertEntriesActivated(ctx, bin)` with one `await auditStartupEntries(ctx, bin)`, optionally passing a `warn` sink to capture optional-failure warnings instead of letting them go to stderr. Stop treating a resolved `Loader.create()` / `boot()` as "everything activated": if the plugin needs a specific sibling capability, audit the entries it cares about *after* settlement, the way the preset mount path does with `await inactiveRows(tree)`. Do not depend on rollback after a rejected plugin candidate — re-check the tree after a config edit and report the failure visibly instead of assuming the previous generation came back. Where the plugin needs package metadata, use `ctx.pluginPackages.packageOf(specifier, parentURL)` rather than requiring a `./package.json` export or walking `node_modules` by hand.
- **Verification**: boot a profile whose root config holds one enabled row that fails to activate and confirm boot rejects with a `required startup failure:` diagnostic when the row id is in the list, and only writes a `warning:` line when it is not — with the other rows still active in the second case. Add a row that injects the renamed service and confirm the diagnostic names it as `pending (waiting for services: …)` rather than silently succeeding.

### DSH-0.1.6-A1-03 · `Session.eventAt()`, `Session.snapshotEvents()` and `Session.ownEvents()` are deprecated and new production calls are prohibited



- **Type**: behavior
- **Applies to**: Host plugins that read Session history — projection, export and query plugins, title generators, telemetry, custom compaction or fork logic — and any plugin whose build runs the repository lint rules.
- **Touchpoints**: #2 for the session-history read contract and the persistent events it exposes; #3 for the `ctx.sessions` service methods.
- **Action level**: required-if-hit
- **Symptoms**: the three readers still exist and still work, but on 0.1.6-alpha.1 they carry an explicit prohibition and the repository enforces it with `typescript/no-deprecated`. `packages/core/session/src/index.ts:627` now reads `@deprecated Existing logic may remain unmigrated for now, but new calls are prohibited.` above `eventAt(seq: SessionSeq): SessionEvent | undefined {` at `:632`; the same tag sits at `:640` above `snapshotEvents(fromSeq: SessionLogOffset = SessionLogOffset(0), toSeqExclusive: SessionLogOffset = this.seq): readonly SessionEvent[] {` at `:646` and at `:659` above `ownEvents(): readonly SessionEvent[] {` at `:663`. On rc.2 those same three methods are at `:621`, `:633` and `:648` with no `@deprecated` tag anywhere in the file. Nothing changes at runtime yet — the decision states the current implementation "still retains the complete event sequence in memory" — but the prohibition is a forward-looking contract: the storage direction will stop keeping the whole sequence resident, and the deprecation is how that dependency is bounded. A plugin that re-exports or wraps these three names under an alias is explicitly prohibited too, and a plugin that reads history in a hot path will be the one that breaks when the residency guarantee ends.
- **Migration recipe**: for "what state does this session have now", read the registered projection instead of scanning history, and for user-requested history use the explicit asynchronous paged read path rather than `snapshotEvents()` over the whole log. Where a complete historical sequence is genuinely required (forking, migration, invariant checks), keep the call and add a line-scoped waiver comment naming the reason — the repository's own callers do exactly that, e.g. `// oxlint-disable-next-line typescript/no-deprecated -- Existing Session history read; migration deferred.` in `packages/api/session-controller/src/index.ts`, `packages/api/session-controller/src/history.ts`, `packages/session/session-projection/src/index.ts` and `packages/core/session/src/invariant.ts`. Do not add an alias or thin wrapper that re-exposes synchronous historical access, and if the plugin publishes its own reader with one of these names, rename it — the lint allowance covers only the three exact names.
- **Verification**: run the plugin's lint/typecheck and confirm no unwaived `eventAt`, `snapshotEvents` or `ownEvents` call remains in production source (test files are exempt; other deprecated names are not). Then exercise the projection path that replaced a call and confirm the resumed session renders the same state the history scan produced before.

### DSH-0.1.6-A1-04 · `ctx.sessions.registerMessageProjection()` is new, and an event that rewrites message content is refused without a registered pure interpreter



- **Type**: capability
- **Applies to**: Host plugins that declare a `SessionEventMap` event changing the content of an existing message, and detached or offline readers (exporters, replay harnesses, query plugins, browser-safe validators) that fold a session log themselves.
- **Touchpoints**: #2 for the event-declaration contract and the required-on-read inventory; #3 for the `ctx.sessions` registration method and the detached `foldSurface`/`deriveEventMessage` entry points; #5 for the registration-as-effect pattern.
- **Action level**: required-if-hit
- **Symptoms**: rc.2 has no message-projection concept at all: `packages/core/session/src/surface.ts:182` declares `export interface SurfaceFoldResult`, `:487` declares `export function foldSurface(events: readonly SessionEvent[]): SurfaceFoldResult`, and `:92` declares `export function deriveEventMessage(event: SessionEvent): Message | null`. On 0.1.6-alpha.1 Session owns a registry: `packages/core/session/src/index.ts:925` adds `registerMessageProjection(projection: SessionMessageProjection): () => Promise<void>` on the `ctx.sessions` store, throwing `session message projection "<type>" is already registered` for a second owner (`:926-:928`), with `get messageProjections(): readonly SessionMessageProjection[]` at `:914` for detached callers. The definition is `export interface SessionMessageProjection<T extends SessionEventType = SessionEventType>` at `packages/core/session/src/surface.ts:35`, requiring `type: T` (`:37`) and a pure `project(event: SessionEvent<T>, context: SessionMessageProjectionContext): ReadonlyMap<SessionSeq, Message>` (`:46`); the context (`:23`) carries `nodes`, `events`, `baseSeq` and `messages`. The fold signature widened to `foldSurface(events: readonly SessionEvent[], projections: readonly SessionMessageProjection[] = [])` at `:544`, and `SurfaceFoldResult` (`:214`) gained `projectedMessages: ReadonlyMap<SessionSeq, Message>` (`:220`) and `readonly contentGeneration: number` (`:230`); `deriveEventMessage` (`:119`) gained a second parameter `projectedMessages?: ReadonlyMap<SessionSeq, Message>` (`:121`). The sharp edge is the refusal: `planSurfaceEvent` throws `session event "<type>" requires a message projection; load its owning plugin or supply its projection definition` when the event type is in the generated inventory `MESSAGE_PROJECTION_EVENT_TYPES` (`packages/core/session/src/known-event-types.ts:82-:85`, currently `{'image/offload'}`), and a definition removed after use invalidates cached reads with `session message projection "<type>" was removed or replaced; restore the session with its owning plugin`. `packages/core/session/src/index.ts:28` newly re-exports `SessionMessageProjection` and `SessionMessageProjectionContext` from `./surface.ts`.
- **Migration recipe**: if the plugin owns an event that rewrites an existing message's content, tag its `SessionEventMap` member with `@messageProjection`, implement a pure `SessionMessageProjection` (`type` plus `project()`), and register it from the plugin's own fiber with `ctx.sessions.registerMessageProjection(def)`, keeping the returned disposer so unloading the fiber removes it.
