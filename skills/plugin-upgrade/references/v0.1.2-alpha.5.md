### DSH-0.1.2-A5-01 · `DomainSpec.compatibleVersions`: per-record reads and the legacy bootstrap accept vouched-for older versions

- **Type**: capability
- **Applies to**: host-plane and author-migrated plugins that persist their own state through the storage-domain API (`defineDomain` from `@deepseek-ai/dsh-storage-domain`, opened through the storage service's `DomainFacility.open`); Cordis plugins that consume the storage service catalog (the `DomainSpec` / `KvUnitDescriptor` declarations); profile wrappers that route storage domains to a backend
- **Touchpoints**: #4
- **Action level**: optional
- **Symptoms**: nothing changes unless a spec declares the field. On a `per-record` layout a stored document whose version stamp is not the unit's current `version` is FOREIGN and reads as absent — the silent-discard contract is unchanged. With `compatibleVersions` declared, the json per-record backend accepts documents stamped with any listed version, and the one-time legacy whole-unit bootstrap (`<root>/<name>.json`, the pre-per-record layout) accepts a legacy file whose `unit.version` is in the set. Writes always stamp the current `version`, `single`-layout reads stay exact-version, a stamp outside the set is still foreign, and `defineDomain` rejects entries that are not non-negative integers strictly below `version` (`packages/storage/storage-domain/src/spec.ts:117`).
- **Migration recipe**:
  1. When you bump a domain's `version` and old records still parse under the new zod schemas — declare the fields old records lack as optional — list the old version(s): `compatibleVersions: [3, 4]`. Old-stamped documents then decode as current on read; the first write after such a read re-stamps them current.
  2. When the old shape cannot be tolerated, do not list it: `per-record` silently discards the stale documents and `single` rejects, exactly as before. Compatibility is a declaration the owner vouches for; authoritative data keeps the default.
  3. Backend reach: the tolerance is implemented by the json per-record backend and its legacy bootstrap only. A backend without `compatibleVersions` support (the sqlite storage backend implements neither this nor `backupRecord`) keeps strict-version semantics — check what your profile routes the domain to before relying on the declaration.
- **Verification**: `defineDomain({ version: 5, compatibleVersions: [4] })` passes while `[5]`, `[-1]`, and `[1.5]` throw; open a json per-record unit whose documents are stamped `4` → the records load, stamped `3` without the declaration → absent; after `putRecord` the document file is stamped `5`; a legacy whole-unit file stamped `4` bootstraps when listed and is left alone (unit reads empty) when not.

### DSH-0.1.2-A5-02 · `invalidRecords: 'backup-and-skip'` + optional `KvUnit.backupRecord`: salvage a schema-failing record instead of refusing the whole domain open

- **Type**: capability
- **Applies to**: plugins whose domains hold disposable derived data — caches, projections, indices that a cold read can rebuild from an authoritative source; backends/units that keep one movable document per record (the json `per-record` layout)
- **Touchpoints**: #4
- **Action level**: optional
- **Symptoms**: nothing changes unless a spec declares the policy. The default (absent `invalidRecords`) is unchanged: a stored table record that fails its zod schema at `open` rejects the whole domain with `invalid-record` (`DomainError`), and the global slot always rejects. With `invalidRecords: 'backup-and-skip'`, the domain layer moves the failing record's document aside through the optional `KvUnit.backupRecord(table, key)` — the json per-record implementation renames it to `<key>.json.bak.<YYYYMMDDHHmm>`, keeping the bytes for inspection and never reading them again — logs the concrete failure (domain, table, key, destination, zod cause), and continues the open with the record absent. A backend without `backupRecord` (the `single` layout, row stores, sqlite) falls back to the rejecting default, so the declaration is inert there. At alpha.5 only the host's own `session_projcache` domain declares the policy.
- **Migration recipe**:
  1. Declare `invalidRecords: 'backup-and-skip'` only for domains whose records are disposable derived data; authoritative data must keep the default reject-loud path.
  2. Confirm the backend the profile routes the domain to implements `KvUnit.backupRecord`; otherwise keep the default, because the declaration would not change behavior.
  3. Plan the rebuild: after a salvage the record is absent until the owning flow writes it again (the host's cache cold-refolds and checkpoints). Same-minute backups of the same key overwrite each other — the newer bytes win; distinct keys and minutes never collide.
- **Verification**: with the policy declared and a schema-failing record present, `open` resolves, the document is renamed to `*.json.bak.*` on disk, `loadAll` shows the key absent, a later `putRecord` recreates the record fresh, and the log names domain/table/key/destination/cause; without the declaration — or with a backend that has no `backupRecord` — the same unit rejects with `invalid-record`.
- **Source**: [compare dsh-v0.1.2-alpha.4...dsh-v0.1.2-alpha.5](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.1.2-alpha.4...dsh-v0.1.2-alpha.5) · `DomainSpec.invalidRecords` contract at [spec.ts:67](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/storage/storage-domain/src/spec.ts#L67) · the open-path salvage at [storage-domain/src/index.ts:131](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/storage/storage-domain/src/index.ts#L131) · `KvUnit.backupRecord` contract at [backend.ts:123](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/storage/storage/src/backend.ts#L123) · json rename implementation at [per-record-unit.ts:238](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/storage/storage-json/src/per-record-unit.ts#L238) · release notes [dsh-v0.1.2-alpha.5](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.5) · rationale in [2026-09-02-projcache-cross-version-read-compat.md](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/.agents/notes/implemented/architecture/2026-09-02-projcache-cross-version-read-compat.md)

### DSH-0.1.2-A5-03 · Host fix: upgrading a 0.1.1-rc.2 / 0.1.2-alpha.3 home to alpha.4 could refuse the boot or drop session titles; alpha.5 reads all three `session_projcache` generations

- **Type**: fix
- **Applies to**: hosts upgraded across the 0.1.1-rc.2 / 0.1.2-alpha.3 / 0.1.2-alpha.4 on-disk generations — anyone upgrading an existing `$DSH_HOME` (registry install or source checkout) rather than starting fresh; plugin authors whose users reported "the app will not start" or "session titles are gone from the list" after upgrading to alpha.4
- **Touchpoints**: none (host persistence surface)
- **Action level**: informational
- **Symptoms**: two failure shapes on alpha.4 when an already-used home was upgraded. (1) From a v3 home (shipped by 0.1.1-rc.2, single-file `storages/session_projcache.json`): the per-record bootstrap migrated the legacy file without checking its `unit.version`, stamping the old records with v5 into the new tree; the domain open then rejected them (`invalid-record` — the lineage fields `isSeeded` / `inheritedEventCount` were required at alpha.4) and the whole domain refused to load, so the plugin tree failed at boot. Because the bootstrap wrote before validation ran, the first boot permanently "poisoned" the new tree: every later boot saw a non-empty tree, never took the legacy path again, and the home stayed unusable. (2) From a v4 home (shipped by 0.1.2-alpha.3, per-record): v4 documents were silently discarded by the strict version-stamp check, and SessionList is a cache-only zero-I/O read, so the list served rows without projections and titles only reappeared as each session was individually reopened.
- **Migration recipe**: upgrade the host to alpha.5 — no plugin code change is required for any of these symptoms. The host's `session_projcache` domain now declares `version: 5, compatibleVersions: [3, 4]` with the two lineage fields optional, so: pristine v3 single-file homes bootstrap and serve titles immediately; "poisoned" v5-stamped-lineageless documents self-heal (they parse under the optional schema and their content is the real pre-upgrade cache data); v4 documents read directly. Stale rows of forked (seeded) sessions still fail the identity match — `identityMatches` normalizes absent lineage to the unseeded shape at [session-projection-cache/src/index.ts:372-381](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/session/session-projection-cache/src/index.ts#L372) — and are discarded to a cold rebuild, the safe side. Deployment caveat: a profile that routes this domain to the sqlite backend gets none of the tolerance (strict-version semantics), because sqlite implements neither `compatibleVersions` nor `backupRecord`; shipped compositions route it to json. Plugin-side corollary: this edge is the host itself applying the storage-domain vocabulary now available to plugins — cross-reference [DSH-0.1.2-A5-01](#dsh-012-a5-01--domainspeccompatibleversions-per-record-reads-and-the-legacy-bootstrap-accept-vouched-for-older-versions) and [DSH-0.1.2-A5-02](#dsh-012-a5-02--invalidrecords-backup-and-skip--optional-kvunitbackuprecord-salvage-a-schema-failing-record-instead-of-refusing-the-whole-domain-open).
- **Verification**: boot the host against `dsh-v0.1.2-alpha.5` on homes of all four shapes (pristine v3, poisoned v3, v4, fresh): the app starts and the SessionList RPC returns the recorded titles verbatim. Upstream's archived-fixture recovery tests do exactly this through the real storage stack: [tests/fixtures.spec.ts](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/session/session-projection-cache/tests/fixtures.spec.ts) plus `tests/fixtures/v3-single-unit.json`, `v4-session-doc.json`, `v5-lineageless-doc.json`, and `v5-session-doc.json` (media archives produced by the real released builds).
- **Source**: [release notes dsh-v0.1.2-alpha.5](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.5) ("Fix an issue where upgrading from 0.1.1-rc.2 or 0.1.2-alpha.3 could prevent the app from starting or make session titles disappear from the list") · implemented architecture note [2026-09-02-projcache-cross-version-read-compat.md](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/.agents/notes/implemented/architecture/2026-09-02-projcache-cross-version-read-compat.md) (problem, three generations, upgrade matrix, alternatives) · projcache domain declaration and identity normalization at [session-projection-cache/src/index.ts:372-381](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/session/session-projection-cache/src/index.ts#L372) · fixture tests at [fixtures.spec.ts](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.5/packages/session/session-projection-cache/tests/fixtures.spec.ts) · [compare dsh-v0.1.2-alpha.4...dsh-v0.1.2-alpha.5](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.1.2-alpha.4...dsh-v0.1.2-alpha.5)

- **Storage-layer reproduction** (Windows 11, 2026-09-03, npm packages `@deepseek-ai/dsh-storage*` at `0.1.2-alpha.4` vs `0.1.2-alpha.5`, isolated temp homes, one scenario script run against each cohort's installed packages): alpha.4 reproduced both failure shapes — under a v5 per-record descriptor, documents stamped 3/4/9 all read as absent and the unit has no `backupRecord` member; a v3 whole-unit home opened under a strict v5 schema rejects with `invalid-record` (the unguarded bootstrap migrates and poisons), and the same home still rejects when the (unknown at alpha.4) salvage declaration is present. - **Real-host validation**: performed on `dsh-v0.1.2-rc.1`, which is alpha.5 plus the version-bump commit — see the record in [v0.1.2-rc.1.md](v0.1.2-rc.1.md#real-host-validation-macos-2026-09-03). Relevant to this edge: a `$DSH_HOME` that had already been through alpha.2 → alpha.4 booted with cached session titles present and **zero** `*.json.bak.*` files, i.e. the new salvage path was armed but not triggered; the previous generation's projection-cache records were read as compatible.
- **Not verified here**: a full host boot with the web client's SessionList (the A5-03 verification section above relies on the upstream archived-fixture recovery tests); Linux hosts; a profile that routes `session_projcache` to the sqlite backend.
- **Conclusion**: for plugins that stay on `defineTool`, the Remote wire, presets, or client UI, alpha.4 → alpha.5 is a restart-only edge with zero code changes. Plugin storage-domain authors gain two optional capabilities (`compatibleVersions` read tolerance, `backup-and-skip` salvage for disposable derived data); adopters must confirm their backend implements them. Hosts upgrading an existing rc.2/alpha.3-era home had real boot/title bugs on alpha.4 and should move to alpha.5 (A5-03). As on earlier edges (rollup R-11), the release notes under-describe the change: they announce only the boot/title fix, while the two storage-domain capabilities exist only in the tag's source — which is why every card above is pinned to the tag rather than to the notes.
