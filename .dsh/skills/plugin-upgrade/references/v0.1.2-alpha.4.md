### DSH-0.1.2-A4-01 · The `report` subagent tool package is gone; `send_message` replaces it

- **Type**: breaking
- **Applies to**: profile wrappers / bundle patches / agent presets that list `@deepseek-ai/dsh-tool-subagent-report` or the `tool-subagent-report` id; plugins and prompt material that tell a continuable child agent to call `report`
- **Touchpoints**: #5
- **Action level**: required-if-hit
- **Symptoms**: `packages/subagent/tool-subagent-report` no longer exists at alpha.4, and the base bundle dropped both its `cordis.patch.yml` row and its `package.json` dependency. A profile or patch layer that still inserts the package fails to resolve it at boot; a prompt that instructs a child to "call `report` when done" refers to a tool that is not registered. Parent ↔ child follow-up traffic now goes through the bidirectional `send_message` tool of `tool-subagent-control` (the child addresses its parent, the parent addresses its direct continuable child).
- **Migration recipe**:
  1. `grep -rn 'tool-subagent-report\|subagent-report' <profile dir> <plugin repo>` — remove every insert/override row and manifest dependency that names the package (at alpha.3 the base bundle listed it at `packages/bundle/base/cordis.patch.yml:376-377`; the `agent-team-profile` and `agent-presets` layers referenced it too).
  2. Rewrite prompt/system-prompt material: "report back with `report`" → "send follow-ups with `send_message` (`agentId` = your direct parent or direct continuable child)". The tool schema is in `packages/subagent/tool-subagent-control/src/index.ts:29-44` at alpha.4; do not invent extra parameters.
  3. If a plugin enumerates the child's tool layer by name (a capability filter), check that the filter still lets the child's structured-output tool through — the alpha.4 comment at `packages/core/tools/src/index.ts` was rewritten to say the delegation runtime registers only the structured-output tool into the child's layer.
- **Verification**: boot the profile against `dsh-v0.1.2-alpha.4`; the plugin inventory (Settings → Plugins → Plugin list) shows `tool-subagent-control` enabled and no `tool-subagent-report` row; a continuable child agent can answer a parent follow-up through `send_message`.
- **Source**: [alpha.4 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.4) ("`send_message` … replacing the one-way `report` tool") · package removal in [compare dsh-v0.1.2-alpha.3...dsh-v0.1.2-alpha.4](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.1.2-alpha.3...dsh-v0.1.2-alpha.4) (`packages/subagent/tool-subagent-report/` deleted; `packages/bundle/base/cordis.patch.yml` and `packages/bundle/base/package.json` drop the row/dependency) · `packages/subagent/tool-subagent-control/src/index.ts:29` at `dsh-v0.1.2-alpha.4`

### DSH-0.1.2-A4-02 · `@deepseek-ai/dsh-code-runtime-python` is renamed to `@deepseek-ai/dsh-experimental-code-runtime-python`

- **Type**: breaking
- **Applies to**: profile wrappers / packaging that depend on the Python code runtime package by name
- **Touchpoints**: none (packaging surface)
- **Action level**: required-if-hit
- **Symptoms**: the package moved from `packages/code-runtime/code-runtime-python` to `packages/experimental/code-runtime-python` and its manifest name changed from `@deepseek-ai/dsh-code-runtime-python` (alpha.3) to `@deepseek-ai/dsh-experimental-code-runtime-python` (alpha.4). ### DSH-0.1.2-A4-03 · `Session.events` is removed; read the log through `seq` / `eventAt()` / `snapshotEvents()` / `ownEvents()`

- **Type**: breaking
- **Applies to**: host-plane plugins and persistence/transport integrations that read a `Session` object's event log (`session.events`, `session.events.length`, `session.events[i]`, `session.events.at(-1)`, spread copies)
- **Touchpoints**: #2 (persistent events), #3 (Remote `history` requests)
- **Action level**: required-if-hit
- **Symptoms**: `Session` no longer has an `events` getter at alpha.4. TypeScript fails with "Property 'events' does not exist on type 'Session'"; untyped JavaScript reads `undefined` and then throws on `.length` / index access. The replacement API is read-on-demand: `session.seq` is the current log length (a `SessionLogOffset`), `session.eventAt(seq)` returns one accepted, deeply frozen event, `session.snapshotEvents(fromSeq?, toSeqExclusive?)` materializes a frozen snapshot of a half-open range (the complete snapshot is cached until the next append), and `session.ownEvents()` returns the events this session appended itself (excluding the fork-inherited prefix).
- **Migration recipe**: old → new ledger —
  - `session.events.length` → `session.seq`
  - `session.events[i]` → `session.eventAt(SessionSeq(i))` (validates the number; see A4-04)
  - `session.events` (whole log) → `session.snapshotEvents()`
  - `session.events.slice(a, b)` → `session.snapshotEvents(SessionLogOffset(a), SessionLogOffset(b))`
  - "events written by this session, not by the fork parent" → `session.ownEvents()`
  - Remote face: the `history` request's `atSeq` is now validated as a non-negative **safe** integer and rejected with `gateway/bad-request` ("atSeq must be a non-negative safe integer") — `packages/api/session-controller/src/commands.ts:193` at alpha.4; `SessionPromptRequest` itself is unchanged (`requestId` / `sessionId` / `mode` / `content` were already required at alpha.2).
  - Do not cache the array returned by `snapshotEvents()` across appends when you need live data; re-read `seq` and call again.
- **Verification**: `tsc --noEmit` of the plugin against `@deepseek-ai/dsh-session` at `dsh-v0.1.2-alpha.4` passes with no `events` access; a runtime read of a live session through the new API returns the same event count as the projection/turn count shown in the web client.
- **Source**: [alpha.4 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.4) ("Replace `Session.events` with on-demand read APIs") · `packages/core/session/src/index.ts:588-629` (`eventAt` / `snapshotEvents` / `ownEvents` / `isOwnSeq` / `get seq`) and `packages/core/session/README.md:54` at `dsh-v0.1.2-alpha.4` · `packages/api/session-controller/src/commands.ts:193` at `dsh-v0.1.2-alpha.4`
- **Field note** (2026-09-02, macOS, source checkout `dsh-v0.1.2-alpha.4`): none of the seven plugins in the verified fleet (a 13-tool Cordis tool plugin with raw wire clients, a cron plugin, three link-installed tool plugins, `dsh-better-sidebar@0.18.0-alpha.0`, `@omdsh-dev/dsh-genui@0.9.6`) read `Session.events` directly, so the ledger above is source-derived, not field-hit. Plugins that only go through `defineTool` / the Remote wire needed no change.

### DSH-0.1.2-A4-04 · `SessionSeq` / `SessionLogOffset` become branded numbers; `seedLength` becomes `isSeeded` + `inheritedEventCount`

- **Type**: breaking
- **Applies to**: host-plane plugins that create agents or sessions with seeded/forked logs (`CreateAgentOptions`, `CreateSessionOptions`, `RestoredSessionOptions`), projection definitions (`ProjectionDefinition.init`), and any code that carries sequence numbers as plain `number` into `@deepseek-ai/dsh-session` / `@deepseek-ai/dsh-agent` types (`AgentState.openTurnStartSeq`, `lastStepStartSeq`, `lastStepBoundary.seq`, `SessionEventWindow.startSeq/endSeq`)
- **Touchpoints**: #2, #5
- **Action level**: required-if-hit
- **Symptoms**: `SessionSeq` and `SessionLogOffset` are now `BrandedNumber` types with constructor functions of the same name (`SessionSeq(value)` / `SessionLogOffset(value)`) that throw `TypeError` on anything but a non-negative safe integer. Plain `number` no longer type-checks where a seq or offset is expected; `null` seq slots use `OptionalSessionSeq` (`SessionSeq | null`) and cursors use `SessionSeqCursor` (`SessionSeq | -1`). The agent/session metadata field `seedLength?: number` is gone: fork seeding is now `meta.isSeeded?: boolean` plus a top-level `inheritedEventCount?: SessionLogOffset` (the exact inherited prefix length). `ProjectionDefinition.init` receives `(header, inheritedEventCount: SessionLogOffset)`.
- **Migration recipe**:
  1. Wrap every seq/offset you construct: `SessionSeq(n)` for event positions, `SessionLogOffset(n)` for lengths/boundaries (both exported from `@deepseek-ai/dsh-session` / `@deepseek-ai/dsh-session/types`). Values you receive from the host are already branded; pass them through untouched.
  2. `meta: { seedLength: n }` → `meta: { isSeeded: true }, inheritedEventCount: SessionLogOffset(n)` on `CreateAgentOptions` / `CreateSessionOptions`; `RestoredSessionOptions` requires `inheritedEventCount`.
  3. Projection definitions: change `init(header, seedLength)` to `init(header, inheritedEventCount)` and treat the second argument as a `SessionLogOffset`.
  4. Where you compared `openTurnStartSeq !== null` or `lastStepBoundary.seq`, the comparisons still work (branded numbers are numbers at runtime); only the declared types need updating.
- **Verification**: `tsc --noEmit` against the alpha.4 packages; at runtime, `SessionSeq(-1)` and `SessionLogOffset(1.5)` throw `TypeError`, and a freshly forked session in the same process shows `session.inheritedEventCount === session.firstLiveSeq` (for a resumed session the two differ: `firstLiveSeq` is the full stored log length while `inheritedEventCount` keeps the original fork cut).
- **Source**: [alpha.4 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.4) ("Distinguish `SessionSeq` and `SessionLogOffset` with strong types; developers should pay attention to compatibility") · `packages/core/session/src/types.ts:29-62` (`SessionSeq`, `SessionLogOffset`, `SessionSeqCursor`, `OptionalSessionSeq`) · `packages/core/agent/src/index.ts:76-94` (`isSeeded`, `inheritedEventCount`, `seedLength` removed) · `packages/session/session-projection/src/index.ts:62` (`init(header, inheritedEventCount: SessionLogOffset)`) · `packages/api/session-controller/src/commands.ts` fork path (`isSeeded: true`, `inheritedEventCount: cut`) — all at `dsh-v0.1.2-alpha.4`
- **Cross-reference**: extends [DSH-0.1.2-A1-27](v0.1.2-alpha.1.md#dsh-012-a1-27--session-content-reads-now-go-through-the-sessionbinding-durable-event-window) (the durable event window introduced at alpha.1): the window's `startSeq` / `endSeq` are `SessionSeq` from alpha.4 on.

### DSH-0.1.2-A4-05 · The `ptc` preset no longer publishes the general `workflow` tool

- **Type**: behavior
- **Applies to**: profile wrappers / presets derived from the shipped `ptc` preset; prompt material that tells a PTC-mode agent to use `workflow`
- **Touchpoints**: #5
- **Action level**: conditional
- **Symptoms**: in Web PTC mode the model no longer sees a `workflow` tool by default; `run_code` is the single model-authored orchestration surface. The `tool-workflow` row in `packages/preset/agent-presets/presets/ptc/agent.cordis.yml` is kept only as engine infrastructure for `ralph` (comment at lines 235-236) and is disabled for the model. - **Migration recipe**: if your preset extends `ptc` and relied on `workflow`, either re-enable `tool-workflow` in your own preset layer or rewrite the instructions around `run_code`; if your preset does not extend `ptc`, nothing changes. Do not "fix" this by editing the shipped preset file — override in your profile layer.
- **Verification**: open Settings → Plugins → Plugin list, switch the session preset selector to the PTC preset: `tool-workflow` shows as disabled while `workflow-worker-thread` and `tool-ralph` stay enabled; the upstream test "omits the general workflow tool only from PTC while retaining Ralph infrastructure" encodes the same expectation.

### DSH-0.1.2-A4-06 · The base bundle enables `web_fetch` by default

- **Type**: behavior
- **Applies to**: profile wrappers built on `@deepseek-ai/dsh-base` (Python SDK, Headless, ACP, custom profiles) that previously relied on `web_fetch` being off unless a preset enabled it; products with a stricter network policy
- **Touchpoints**: #5
- **Action level**: conditional
- **Symptoms**: `tool-web` in the base bundle now carries `config: { fetch: true }` (`packages/bundle/base/cordis.patch.yml:461-464`), so agents in non-web products get `web_fetch` alongside `web_search` without any preset opting in. A deployment that assumed "no outbound fetch unless enabled" now has one.
- **Migration recipe**: profiles that must not fetch override the row in their own patch layer (`- id: tool-web` with `config: { fetch: false }`); profiles that previously enabled fetch per preset can drop that override. Treat this as a policy review item, not a code change.
- **Verification**: boot the profile and list the model-facing tools of a new session (Plugin list → `tool-web`, or a first prompt asking the agent to enumerate its tools): `web_fetch` is present when you expect it and absent when you overrode it; the upstream bundle test now expects `{ fetch: true }`.
- **Source**: [alpha.4 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.4) ("Enable `web_fetch` by default for the Python SDK, Headless, ACP, and custom Profiles") · `packages/bundle/base/cordis.patch.yml:461-464` at `dsh-v0.1.2-alpha.4` and the bundle test expectation flip `fetch: false` → `fetch: true` in the [compare view](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.1.2-alpha.3...dsh-v0.1.2-alpha.4)
