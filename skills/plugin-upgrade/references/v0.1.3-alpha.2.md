### DSH-0.1.3-A2-01 · deployment persona splits into prefix + suffix (`text`/`persona` config keys and `PERSONA_SECTION` removed)

- **Type**: breaking
- **Applies to**: profile compositions and Agent Presets that configure persona rows
  (`dsh-persona` / `dsh-system-prompt` rows in `cordis.patch.yml` and `agent.cordis.yml`),
  and any plugin or wrapper that imports `PERSONA_SECTION` (or the `deployment:persona`
  section name) or the old config keys.
- **Touchpoints**: none (composition/config surface); #1 only for source patches that
  target the old section name or config key.
- **Action level**: required-if-hit
- **Symptoms**: on 0.1.3-alpha.2, `PERSONA_SECTION`/`deployment:persona` is gone and the
  persona config keys were renamed:
  - `dsh-persona` (packages/preset/persona) plugin `Config.text: string` → `Config.prefix:
    string` + optional `Config.suffix`; re-exported constant `PERSONA_SECTION` →
    `PERSONA_PREFIX_SECTION` / `PERSONA_SUFFIX_SECTION`;
  - `dsh-system-prompt` (packages/core/system-prompt) plugin `Config.persona` →
    `Config.personaPrefix` (+ suffix counterpart), section-order slot
    `DEPLOYMENT_PERSONA` → `DEPLOYMENT_PERSONA_PREFIX` (+ `DEPLOYMENT_PERSONA_SUFFIX`),
    and section names `deployment:persona` → `deployment:persona-prefix` /
    `deployment:persona-suffix`;
  - the shipped base bundle row changed `persona: ''` → `personaPrefix: ''`
    (packages/bundle/base/cordis.patch.yml).
  A composition that still writes the old keys no longer produces the intended persona
  text (the text slot it targeted no longer exists), and code importing `PERSONA_SECTION`
  fails typecheck with a removed-member error.
- **Migration recipe**: split the deployment-authored persona into the prefix (rendered
  before first-party guidance) and an optional suffix (rendered after it): rename
  `text` → `prefix` (+ `suffix`) in `dsh-persona` rows and `persona` → `personaPrefix`
  (+ the suffix counterpart) in `dsh-system-prompt` rows; the `complete: true` policy now
  means "the prefix is the complete system prompt, suppressing the suffix and every other
  section". Scoped sections and imports must use the two new names. Because the exact
  suffix config key and shadowing semantics are newer than the release note's one-line
  summary, re-check the target tag's types (`packages/preset/persona/src/index.ts`,
  `packages/core/system-prompt/src/index.ts`) before rewriting rows — do not guess the
  shape from this card.
- **Verification**: `dsh --profile <p> --dump-config` shows the renamed rows with no
  validation errors; a cold start renders the prefix before first-party guidance and the
  suffix after it (inspect the assembled system prompt); the old-key row shape is
  confirmed gone, not silently ignored.
- **Source**: [alpha.2 persona plugin source](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/packages/preset/persona/src/index.ts) · [alpha.1 persona plugin source (old `text` key)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/preset/persona/src/index.ts) · [alpha.2 system-prompt sections](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/packages/core/system-prompt/src/index.ts) · [alpha.2 base bundle persona row](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/packages/bundle/base/cordis.patch.yml) · [0.1.3-alpha.2 release notes (custom persona config split)](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.2)

### DSH-0.1.3-A2-02 · `SubprocessHandle.pid` removed from the subprocess seam (terminal handle keeps `pid`)

- **Type**: breaking
- **Applies to**: plugins and integrations that spawn processes through the
  `@deepseek-ai/dsh-subprocess` seam and read `SubprocessHandle.pid` (process
  supervision, kill-by-pid, pid-based logging or UI). Terminal flows
  (`SubprocessTerminalHandle`) are not affected.
- **Touchpoints**: #7
- **Action level**: required-if-hit
- **Symptoms**: `pid: number` is removed from `SubprocessHandle` in
  `packages/subprocess/subprocess/src/types.ts`; `SubprocessTerminalHandle.pid` remains.
  Code doing `handle.pid` fails typecheck (removed member) and, if it relied on the
  numeric pid at runtime (signalling, `taskkill`/`kill` by pid, reuse detection), has no
  replacement value. Termination semantics are also re-worded per provider: each
  subprocess provider documents the process range it can observe and its signalling and
  observation limits, with termination and `waitForExit` using the same managed range.
- **Migration recipe**: replace pid-based control with the handle verbs: terminate
  through the handle (the seam's documented escalation, idempotent once the managed tree
  is gone) or the spec's abort signal, and observe exit through `waitForExit` /
  collected streams. If the pid was only shown to users (for example in a process list),
  remove the column or surface provider-reported identity instead; do not re-derive a
  pid from the terminal handle for non-terminal handles — the types no longer promise
  one. Re-check `packages/subprocess/subprocess/src/types.ts` and the provider you use
  (`subprocess-local`, `subprocess-e2b`, win32) at the target tag for the exact verbs.
- **Verification**: typecheck passes without `handle.pid`; a spawn → terminate →
  `waitForExit` cycle works for each provider you support; abort-path tests cover both
  normal exit and kill escalation; UI/log surfaces that previously printed the pid show
  the new identity or nothing.
- **Source**: [alpha.2 subprocess types (no `SubprocessHandle.pid`; terminal handle keeps it)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/packages/subprocess/subprocess/src/types.ts) · [alpha.1 subprocess types (pid present)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/subprocess/subprocess/src/types.ts) · [alpha.2 runner protocol](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/packages/subprocess/subprocess-local/src/runner-protocol.ts) · [0.1.3-alpha.2 release notes (plain subprocess handle drops pid)](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.2)

### DSH-0.1.3-A2-03 · default file-editing tooling moves to `read`/`write`/`edit`; shipped base no longer mounts the `tool-str-replace-editor` row

- **Type**: behavior
- **Applies to**: profiles and compositions whose mounted tool set came from the shipped
  bundles (SDK, Headless, ACP first-party flows), and wrappers/presets that referenced
  the `tool-str-replace-editor` loader row by id or that document "which edit tools ship
  by default".
- **Touchpoints**: none (default composition/tool-surface)
- **Action level**: conditional
- **Symptoms**: the alpha.2 shipped `packages/bundle/base/cordis.patch.yml` removes the
  `tool-str-replace-editor` loader row (`@deepseek-ai/dsh-tool-str-replace-editor`,
  `maxOutputChars: 16000`) that alpha.1 still mounted. Release notes state the default
  file-editing tool adjustment: SDK, Headless and ACP use `read`/`write`/`edit` for file
  editing by default, while web minimal and sdk-minimal keep their defaults. The
  str-replace editor package itself still exists at the alpha.2 tag — only the shipped
  default rows moved.
- **Migration recipe**: do not assume which editor tools are mounted — on the target
  version, dump the actual profile composition (`dsh --profile <p> --dump-config`) and
  check the mounted tool rows before writing recipes or docs that name a default editor.
  Custom compositions that explicitly mount `tool-str-replace-editor` keep working only
  while the package remains available; verify against the target tag rather than this
  note. If a productized flow (SDK/Headless/ACP-style) taught users a str-replace
  workflow, re-run it against the `read`/`write`/`edit` default set and update the flow.
- **Verification**: per affected profile, dump-config lists the expected editor rows; a
  real edit round-trip through each affected profile's default editor tool succeeds;
  sdk-minimal / web-minimal behavior is unchanged where the release notes promise it.
- **Source**: [alpha.2 base bundle patch (row removed)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/packages/bundle/base/cordis.patch.yml) · [alpha.1 base bundle patch (row present)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/bundle/base/cordis.patch.yml) · [0.1.3-alpha.2 release notes (default tool adjustment)](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.2)

### DSH-0.1.3-A2-04 · CLI launcher exports `runCli()` behind an `import.meta.main` gate (Node runtime floor)

- **Type**: behavior
- **Applies to**: wrappers, CI matrices and headless launchers that invoke `dsh` as a
  subprocess or import the CLI entry (`lib/bin.js`); ordinary Cordis plugins are not
  affected unless they spawn or import the CLI.
- **Touchpoints**: #7
- **Action level**: conditional
- **Symptoms**: in `apps/cli/src/bin.ts` (and the packed `lib/bin.js`) the top-level
  argument parsing + dispatch moved into `export async function runCli()`, invoked only
  under `if (import.meta.main)`. Command-line behavior is unchanged on supported Node
  runtimes, but: (a) importing the entry module no longer has CLI side effects — code
  that imported `lib/bin.js` for its side effects now gets an inert module plus the
  `runCli` export; (b) `import.meta.main` requires a modern Node (`≥24.2` per the
  official v24.2 blog; backported to the 22.18+ line per community tracking) — on older
  Node the main-execution branch never runs, so `dsh` produces no output and exits 0.
  Both alpha.1 and alpha.2 pack no `engines` field, so the floor is not enforced by npm.
- **Migration recipe**: pin the Node runtime your wrappers/CI use to a version that
  supports `import.meta.main` (22.18+ LTS or ≥24.2) and assert it in smoke tests: run
  `dsh --version` and require non-empty output with a non-zero exit on failure — a
  silent empty run on old Node is the failure mode to catch. Programmatic users should
  call `runCli()` explicitly instead of relying on import side effects.
- **Verification**: on the pinned Node, `dsh --version` prints and exits 0; on an old
  Node in the test matrix, the smoke test fails loudly instead of silently passing; a
  `node -e "import('@deepseek-ai/dsh/lib/bin.js').then(m => console.log(typeof m.runCli))"`
  check prints `function` without running the CLI.
- **Source**: [alpha.2 CLI entry](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/apps/cli/src/bin.ts) · [alpha.1 CLI entry (top-level dispatch)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/apps/cli/src/bin.ts) · [0.1.3-alpha.2 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.2) · tag diff `apps/cli/src/bin.ts` (`dsh-v0.1.3-alpha.1...dsh-v0.1.3-alpha.2`)

### DSH-0.1.3-A2-05 · `dsh-llm-pi-ai` bumps `@earendil-works/pi-ai` `^0.84.2` → `^0.85.1` (duplicate-instance trap for direct dependents)

- **Type**: behavior
- **Applies to**: plugins that depend on `@earendil-works/pi-ai` directly (for example
  to build their own pi-ai-backed adapter), or that import from
  `@deepseek-ai/dsh-llm-pi-ai` internals; host deployments pinning a pi-ai version for
  vLLM thinking-budget options.
- **Touchpoints**: none (packaging/dependency surface)
- **Action level**: conditional
- **Symptoms**: `packages/llm/llm-pi-ai/package.json` moves `@earendil-works/pi-ai` from
  `^0.84.2` to `^0.85.1` (release notes: upgrade to pi-ai 0.85.1 for new-model support;
  the adapter's catalog/config/replay/stream sources changed in the same window). A
  plugin that pins its own older pi-ai copy can end up with two pi-ai instances in one
  tree — the same duplicate-instance trap already carded for the 0.1.2 line
  ([DSH-0.1.2-A1-24](v0.1.2-alpha.1.md)).
- **Migration recipe**: if the plugin depends on `@earendil-works/pi-ai` directly,
  align its range with the host cohort (or prove the override is only serving the older
  peer before keeping it); re-run the adapter's provider/model catalog assertions against
  the new pi-ai; check that identity-sensitive exports (`instanceof`, class tokens)
  resolve to the host's pi-ai copy. Where release notes only promise "new model
  support", verify concrete catalog entries against the alpha.2 tag's
  `packages/llm/llm-pi-ai/src/catalog.ts` rather than assuming a model list from this
  card.
- **Verification**: install/typecheck clean with a single pi-ai copy (lockfile shows one
  resolved instance); a provider round-trip (list providers → model call → replay)
  passes; any duplicate-instance symptoms (`instanceof` failures, two copies in the
  dependency tree) are gone.
- **Source**: [alpha.2 llm-pi-ai package.json (`^0.85.1`)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.2/packages/llm/llm-pi-ai/package.json) · [alpha.1 llm-pi-ai package.json (`^0.84.2`)](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.3-alpha.1/packages/llm/llm-pi-ai/package.json) · [0.1.3-alpha.2 release notes (pi-ai 0.85.1)](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.2) · duplicate-instance precedent [DSH-0.1.2-A1-24](v0.1.2-alpha.1.md)
